# StuTrade Engine

StuTrade 的通用撮合引擎。它以 Go module 嵌入业务宿主，管理挂单、价格撮合和撮合请求；领域规则、持久化和成交后的业务流程由宿主提供。

整个项目的产品范围、架构和跨仓库契约以主仓库 `docs/` 为唯一文档真相源。本 README 只说明 engine 的代码边界和开发方式，不独立扩展产品语义。

## MVP 目标

第一版服务二手书交易，支持三条路径：

1. 自动撮合：卖方报价不高于买方出价时生成撮合请求，双方确认后成交，按卖方报价结算。
2. 卖方接单：卖方选择买方需求，按买方出价直接成交。
3. 买方购买：买方选择卖方供给，按卖方报价直接成交。

所有路径使用同一套撮合规则和状态机。宿主通过引擎定义的 Protocol 注入 ISBN 一致、禁止自买和资源有效性等规则；引擎不提供通用规则语言。

MVP 固定为单件人民币交易，不包含支付、聊天、物流、竞价、多币种、模糊文本匹配和后台撮合任务。

## 责任边界

引擎负责：

- 通用买卖挂单及其状态转换；
- 基础价格兼容判断和候选优先级；
- 撮合请求、双方确认、拒绝和撤单；
- 重复请求、重复确认和并发竞争约束；
- 返回稳定的领域错误，供宿主翻译成外部协议。

宿主负责：

- 图书、ISBN、需求、用户和订单等业务模型；
- 身份认证、HTTP、用户文案、日志和通知；
- 数据库迁移以及 Protocol 的持久化适配；
- ISBN 一致、禁止自买、资源有效性等领域授权；
- 成交后创建订单并推进履约。

依赖方向始终为 `宿主 -> engine`。引擎不得导入宿主代码，也不感知 HTTP、ORM 或具体数据库。

## 核心模型

### Listing

挂单包含宿主生成的 ID、所有者 ID、宿主资源引用、买卖方向、以分为单位的正整数价格、状态和时间信息。

状态转换：

```text
open -----> reserved -----> matched
  |             |
  |             +--------> open       撮合被拒绝
  |
  +----------------------> withdrawn  主动撤回
```

一个挂单同时最多参与一个未完成的撮合请求。撤回已预留挂单时，关联请求取消，未撤回的对手挂单重新开放。

### MatchRequest

撮合请求记录买卖双方挂单、成交价、发起方式、双方确认、状态和宿主订单引用。

```text
pending -----> completed
   |
   +---------> declined
   |
   +---------> cancelled
```

自动撮合创建 `pending` 请求，双方明确确认后完成。直接接单或购买也记录请求，但目标挂单视为挂单方的事前承诺，用户操作视为发起方确认，因此请求在同一事务内直接完成。

## 撮合规则

- 自动撮合仅考虑方向相反、状态开放且 `卖方报价 <= 买方出价` 的挂单。
- 买方侧按卖方报价从低到高选择；卖方侧按买方出价从高到低选择。
- 同价候选按创建时间排序，最后以 ID 打破平局，保证结果稳定。
- 自动撮合以卖方报价成交；卖方接单以买方出价成交；买方购买以卖方报价成交。
- 每条路径都必须调用宿主规则；候选发现时用于过滤，落库前再次校验，防止资源在期间失效。
- 一次撮合只预留一对挂单。MVP 不实现部分成交或一对多成交。

自动撮合由宿主显式触发并同步返回结果。引擎不启动 goroutine，不轮询数据库，也不隐藏异步生命周期。

## 宿主 Protocol

Protocol 是由引擎消费方定义的小型 Go interface 集合，不是一个包含所有宿主能力的大接口。当前首个调用方只需要发布挂单，因此协议保持为单方法能力：

```go
type ListingCreator interface {
	CreateListing(context.Context, *Listing) error
}
```

`PublishListing` 负责构造合法的 open 挂单，再通过该能力持久化。候选查询、事务、宿主规则和订单创建能力会随对应成交用例加入；当前不预先公开没有调用者的接口。引擎不记录日志，宿主在最终处理边界统一记录。

## 公开用例

MVP 只为现有宿主流程提供以下能力，具体 Go 方法签名由首个调用者驱动：

- 发布和撤回挂单；
- 为指定挂单尝试一次自动撮合；
- 对一对明确挂单发起直接接单或购买；
- 确认或拒绝待处理撮合请求；
- 查询单个挂单、撮合请求和用户的待确认请求。

宿主负责浏览图书和需求的读模型。引擎不提供领域搜索接口，也不接受 `map[string]any` 形式的宿主扩展字段；跨边界只保存不透明的宿主资源引用。

## 项目结构

MVP 保持单一根包，按责任拆文件，不预建没有调用者的分层目录：

```text
.
├── doc.go                 包文档
├── engine.go              发布挂单用例编排
├── listing.go             Listing 模型及状态转换
├── match_request.go       MatchRequest 模型及状态转换
├── matching.go            价格规则与候选选择
├── protocol.go            当前调用方所需的最小能力接口
├── errors.go              可由 errors.Is / errors.As 识别的领域错误
├── *_test.go              与被测行为同包放置的测试
├── README.md
└── go.mod
```

只有出现独立责任和真实复用方后才拆子包。测试辅助代码留在 `_test.go`；不要为了目录对称创建 `domain`、`service`、`repository` 或 `utils` 包。数据库适配器、迁移和宿主订单实现位于 `stu-trade` 仓库，不进入本模块。

## 依赖规划

MVP 生产代码默认只使用 Go 标准库：

- `context` 传递取消、截止时间和请求范围；
- `errors` 提供稳定错误判断；
- `fmt` 包装依赖失败并保留原因；
- `sort` 或 `slices` 实现确定性候选排序；
- `time` 表达状态发生时间。

ID 由宿主生成，因此引擎不依赖 UUID 库。金额使用以分为单位的自定义整数类型，不引入 decimal 库。测试优先使用 `testing`，不预先引入断言、mock 或 DI 框架。

ORM、数据库驱动、HTTP 框架、日志库和通知客户端属于宿主。若后续确有第三方依赖，必须有当前调用者，直接记录在 `go.mod`，提交同步的 `go.sum`，并通过 `go mod tidy`、测试和漏洞检查；不得仅为可能的未来需求引入依赖。

## 实施顺序

1. 用表驱动测试确定金额、价格边界、状态转换和错误标识。
2. 实现挂单 Protocol，并在宿主用真实数据库适配器走通“买方购买 -> 创建订单”。
3. 复用同一核心完成卖方接单，不增加 mode 驱动的平行流程。
4. 实现候选发现、自动撮合、双方确认和拒绝释放。
5. 补齐查询入口、三条 E2E 路径以及并发和重试回归。
6. 建立格式化、静态检查、普通测试和竞态测试的 CI。

重点回归场景包括价格等于边界、ISBN 不一致、自买、资源失效、重复确认、同时争抢同一挂单，以及确认与撤单并发。
